# A2UI Android Deep Dive

This is the deep dive. The previous guide got you rendering. This one walks the actual API surface of the alpha libraries, package by package, so you know what exists before you need it. There are two hundred and seventy three public types across twenty packages, and the useful thing is not the count, it is that maybe fifteen of them matter to a normal integration. We will name which fifteen, and what the rest are for. Everything here was read out of the published artifacts, because there is no API reference site for these libraries yet.

Here is how the surface splits. The model artifact is the vocabulary: the protocol types, the processor interfaces, and the function library. The engine is the state machine that drives them. Compose runtime is the binding layer, and it carries roughly half its types purely as a property type system, which we will come back to. Compose UI is small on purpose: twelve types, and it is the contract a renderer implements. And material 3 dash a 2 u i is the largest of the five, a hundred types, because it is a full catalog implementation: eighteen components, their property declarations, the icon set and theming defaults.

Read this as a map of where to look. If you are debugging what arrived on the wire, you want model dot protocol. If the screen is not updating, you want model dot processor. If a bound value is not refreshing, you want compose runtime. If a component draws wrong, you want the catalog implementation. Most alpha debugging is figuring out which of those four layers is lying to you, and knowing the split turns a vague problem into a specific one.

Start with the object you will hold a reference to.

The processor interface is four members and that is the entire runtime contract. Active surfaces is a state flow of surface models, and it is what you collect in Compose. Outbound events is a flow of client to server messages, which is every user action leaving the client. Process message takes one parsed server message. Process error reports a client-side failure back. And collect messages is a suspending function that drains the inbound queue. That last one catches people: it is not optional and it is not fire and forget. If you do not keep it running inside a launched effect for the lifetime of the screen, messages queue up and the surface never changes. A blank screen with no error in logcat is almost always this. Note also the factory takes a list of catalogs and a list of action interceptors, and an interceptor gets to rewrite or swallow a user action before it leaves, which is where you would put logging, redaction or an approval step.

Next, the types that define what can travel between an agent and a client.

Eighteen types, and they divide cleanly. Server to client is four messages: create a surface, update components, update the data model, delete a surface. Client to server is two: an event, and an error. That asymmetry is the shape of the protocol. The agent describes, the client reports. Then the action types. A user action carries the surface, the component and a timestamp. An event action is the one that travels to your agent. A function call action does not travel at all, it invokes a catalog function locally. Underneath sit the supporting types: the client data model with its to payload map, which is how you serialise state to send back; a data path, which is a JSON pointer into the data model; an inline catalog, for sending a catalog definition with the surface instead of by reference; and client capabilities, which is how a client advertises what it can handle.

And here are three of those message types as an agent actually emits them. Create surface names the surface and the catalog. Update components carries an adjacency list, where each entry has an identifier and names its children by identifier, with the entry point called root. Update data model carries the values. Notice this agent sends the components in several update messages rather than one. Nothing requires that, but because components refer to children by name rather than by nesting, a partial tree is perfectly legal, and the client draws what it has.

Now the part of the API that is largest and least discussed.

Roughly twenty eight of the compose runtime types are property declarations, and they are how a component describes its own schema. Every one extends A2UI property, which carries a key, a JSON schema fragment and whether it is required. The split that matters is static versus dynamic. A static property is fixed when the component is sent: a string, a number, an enum, a child list. A dynamic property may instead carry a path, binding it to the data model. Only dynamic properties can be bound, and only bound properties take part in updates. So when you design a custom component, the question for each property is not what type is this, it is can an agent bind this to data, or is it structural. Get that wrong and the component renders once and never reacts. Notice also the enum properties, string enum and number enum: declaring a property that way is what produces the strict validation we hit earlier, where an unexpected variant renders an error chip rather than throwing.

Which brings us to the piece you probably came here for.

Thirteen functions ship in the alpha, and they all implement one interface: a definition describing the signature, and an execute that takes an argument map and an execution context. They group into four kinds. Validation: required, email, numeric, regex and length. Logic: and, or and not, which let an agent compose conditions without sending code. Formatting: format string, format number, format currency, format date and pluralize. And one side effect: open URL. Two details matter in practice. First, the stateless ones are Kotlin objects, so you reference required function dot instance rather than constructing anything. The ones that need locale or a message formatter take that dependency in their constructor, and that is precisely why the Material catalog factory demands a locale provider, a message formatter and a URL opener from you. It is constructing this library on your behalf. Second, and this is the important one: these execute on the client. When an agent marks a field required, or asks for a currency format, no round trip happens. Validation is immediate and offline. You can look any of them up by name from a catalog's function collection at runtime.

So how does a component get registered at all.

This is the whole renderer contract, and it is two interfaces. A component has a name, which is the string an agent puts in the component field; a description; a list of properties, which is the schema we just walked; an optional is ready, which lets a component decline to draw until its data has arrived, and that is how streaming avoids flicker; and a composable content function. A catalog has an identifier, which is the catalog identifier on the wire, a collection of components, a collection of functions, and a theme schema. Both collections are lists with lookup by name. That is it. Nothing in either interface mentions Material, Compose theming or any design system. Material 3 dash a 2 u i is one implementation of A2UI catalog, and because the processor takes a list, yours can sit next to it rather than replace it.

Inside a component, six functions do the work.

The component scope is what your content function receives, and it is six members. Bind reads a dynamic property and recomposes when the underlying data moves. Bind updater hands you a setter, and that is two-way binding: a text field calls it on every keystroke and the client data model updates with no network involved. Bind child references resolves a child list into references you can render. Observe component state gives you a component's state by surface and identifier. Dispatch action fires a user action, which is what surfaces on outbound events and reaches your agent. Report error pushes a client error back. Alongside it, component properties gives typed access to static values, with a contains check for optional ones. In practice a custom component is mostly three of these: bind for reading, bind updater for writing, dispatch action for interaction.

Here is the shape a component implementation takes. These are the media stubs the Material catalog requires, so they are deliberately empty, but the structure is what to look at. Typed content is an extension function on the component scope rather than a plain method, which means the binding functions are in scope inside it without being passed. The accessibility parameter is nullable. And the property list is typed, so the values arriving here have already been validated against the schema the component declared.

And the implementation you get for free.

The Material artifact exposes a small public surface over a large private one. A2UI surface is the composable you hand a surface model to. Surface defaults and Material A2UI defaults carry the theming knobs. And the catalog factory takes those six parameters we have discussed. Behind that sit roughly a hundred types: eighteen components, their property declarations, an icon set and the theme plumbing. Worth saying plainly: if your design system is not Material, you are not stuck with this. You implement the same catalog interface, and the hundred types behind this one are the scale of work you are taking on if you implement all eighteen components yourself.

With the API named, the behaviour we saw earlier reads differently. This form arriving in pieces is create surface, then several update components messages, then update data model. The fields fill last because binding resolves against a data model that arrived after the structure did. And is ready is what stops half-bound components from flickering while that happens.

And this is the same round trip with every piece identified. The checkbox calls bind updater, which writes to the client data model. Tapping review calls dispatch action, which produces a client event message on outbound events, carrying the context and the data model's payload map. Our code posts it, the agent replies, and process message feeds the answer back in. Every step is a name you now know.

One layer we have not opened, and for some of you it is the most important one.

The engine artifact is thirty types and you rarely construct any of them directly, but two are worth knowing. The action handler is what the processor builds internally: it holds your interceptor chain, a way to read the current data model, and a way to send a client to server message. Every user action goes through it. And an action interceptor is a single suspending function that receives a user action and returns one. It can pass it through, rewrite it, or hold it. If you work somewhere that has to prove what left the device, this is your seam: redaction, audit logging, or a human approval step all live here, in one place, rather than scattered across components. The error path is the other half. The runtime throws A2UI exception, a component can report one through its scope, and process error sends a client error message back so the agent learns that its payload failed rather than watching a blank screen.

Everything so far came out of the artifacts. Here is the same API the way you will actually meet it.

First, a practical warning that will cost you an afternoon otherwise. This project needs Android Gradle Plugin nine point four, and the Gradle command line will happily build it on any Studio version, because Gradle does not care what I D E you have. Android Studio does care. On a twenty twenty five release the sync fails outright with an incompatible A G P error, so you get no indexing, no completion and no navigation, while the command line keeps working and tells you nothing is wrong. You want a twenty twenty six release. And add a Gradle wrapper pinned to the version you build with, because without one Studio picks its own and fails with a class not found error that tells you nothing useful.

Once it syncs, this is what you get. Every A2UI symbol resolves, parameter name hints show you what each argument is, and the inlay hints mark usages. The two launched effects are the whole client: one streams a surface in, the other collects outbound events and posts them back. Being able to see the types inline is most of why getting the sync working is worth the trouble.

And here is the fastest way to learn this API. Type processor, then a dot. The completion list is the entire processor interface with its types spelled out. Active surfaces, a state flow of surface models. Outbound events, a flow of client to server messages. Process message, taking a server to client message. Collect messages. Process error. Five members, and the signatures tell you how they connect. With no reference documentation published, completion in a synced project is the most reliable API reference you have.

Two honest gaps to close on. There is no published API reference for these libraries, which is why this video exists: everything here was read out of the artifacts themselves. And the alpha has no compatibility promise, so pin all five to the same version and expect signatures to move. The pieces most likely to shift are the ones with the least documentation, which is the property system and the component scope. If you are building on this now, wrap your own thin layer over the processor and the scope rather than sprinkling library calls through your feature code. Then when alpha two lands, you fix one file. If you are starting on Monday, here is the order that works. Get a project syncing in a twenty twenty six Studio with a pinned Gradle wrapper first, because without indexing you are guessing at every signature. Render a static payload from assets next, so you learn the message types with nothing else moving. Only then point it at a real agent and add outbound events, because debugging streaming and the round trip at the same time is how you lose a day. Keep your own surfaces pre-authored on the server rather than generated, which costs you nothing and means you can show someone exactly what a screen will look like before it ships. And when a component renders as a red error chip, check the enum value before you check your code.
