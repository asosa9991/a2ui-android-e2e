# Non-Deterministic Data Without Generating UI

Here is the constraint most regulated teams end up with. You may not let a model generate user interface at runtime, because every screen a customer sees has to be reviewed before it ships. So you go the template route: pre-authored, reviewed structures, filled with data. That works beautifully as long as the data is predictable. Then you hit a case where it is not. An account with no holdings, or one holding, or four hundred. Groups nested two deep for one customer and flat for another. The instinct is that templates have run out and you now need generated UI. That instinct is wrong, and the rest of this is why.

The answer is already in the protocol, in a place that is easy to read past. A component's children property accepts two different things. The obvious one is an array of child identifiers, a fixed list. The second one is an object: a component identifier, and a path. That says render this one component once for every item in the list at that path. So the number of rows on screen is a property of the data, not of the structure. You write one row, review one row, and the same reviewed structure renders zero rows or four hundred.

Here is that in practice. A column whose children are a template pointing at slash holdings, and the row component it names. That row is two text components bound to symbol and value. Notice those paths have no leading slash. Inside a template, a bare path is relative to the item currently being rendered, so symbol means this item's symbol. The column does not know how many rows there will be, and it does not need to. Nothing here changes when the data does. One more thing to notice: the row itself is a Row component with two children, so it is an ordinary reviewed component in every respect. There is nothing special about being a template. Any component can be one, and the same component can be a template in one place and a plain child somewhere else.

That relative path is doing more work than it appears to.

Because a path inside a template resolves against the current item, a template can contain another template. This is a group block: a card, a title bound to the group's name, and then a column whose children are a template pointing at holdings, with no leading slash. That means this group's holdings. And the component it renders is the same holding row from a moment ago. One reviewed row component, used at two different depths, against two different shapes of data. That is how a fixed component tree renders a structure whose depth and width you did not know when you wrote it. It is worth pausing on why this is safe. The nesting depth is bounded by the components you wrote, not by the data. A group can contain holdings because you said it can. If the data arrives three levels deep and your templates only nest two, you get two levels rendered, not an unexpected screen. The data can change how much you see; it can never invent a shape you did not author.

And this is not theoretical for you, because your own brokerage payload already does it. Four template bindings, two of them relative. Groups render from a template, positions render from a template relative to their group, and the key value row template is used twice at two different depths for two different data shapes. That payload renders three groups, each with a different number of positions, each with a different number of detail rows, from a component tree written once. The pattern you need for non-deterministic data is the pattern already in your repository. Which is the argument to take to your reviewers, because it is not a proposal. It is a description of something already running in your codebase that they have presumably already approved.

So let us push it. Same components, four datasets that look nothing like each other.

This function is the only thing that differs between the four screens you are about to see. Empty. One holding. Forty holdings. And three groups of holdings, nested. Different lengths, different shapes, one with a populated groups list and an empty flat list and one the other way round. The component tree above it is untouched between all four. And note what is not in this function: there is no component identifier, no layout, no branching on which widget to use. It returns values. That is the line you want to be able to point at.

Start with nothing. The template at slash holdings produces no children, so the list renders as nothing at all, and the empty message is a text component bound to a string that happens to have content in this dataset and not in the others. That is worth saying plainly: the empty state is not a different screen, it is the same screen with different data.

Tap through and now there is one holding. The empty message went away because its bound string is now blank. One row appeared because the list at slash holdings has one item. No new components were sent to get here.

Again, and now there are forty. Forty rows, from the same single row component, scrolling. If you were generating this, forty rows would be forty component definitions crossing the network and forty things nobody reviewed. Here it is one reviewed component and a list of forty values. This is also where the performance argument lands. Forty rows of generated components would be forty definitions parsed and diffed. Here the client already has the row and is mapping a list over it, which is the same work a native list adapter does. Bigger data does not mean a bigger payload of structure, it means a longer array of values.

And the last one changes shape entirely: three groups, each holding a different number of positions, rendered by the nested template. Technology with six, financials with three, healthcare with three. Two levels deep, and still the same component tree that drew the empty screen a minute ago. Depth and width both came from the data. And if a fourth dataset arrived tomorrow with ten groups instead of three, or three levels instead of two where your templates support it, nothing here would need rebuilding or re-reviewing. That is the property you are actually buying.

That is the visible half. The wire tells the other half of the story.

Here is the agent's log for that whole sequence. One create surface and one update components at the start, and after that, only update data model. Three times. The structure crossed the network once, at the beginning, and never again. Every screen change after that was data. That has three consequences worth caring about. It is small, because you are sending values rather than a tree. It is fast, because the client is diffing a data model rather than rebuilding components. And it is auditable, because the structure a customer saw is a known artifact and the only variable is the data you can log alongside it. It also means a re-render is cheap enough to do often. If holdings update every few seconds, you are sending a small data model, not a screen.

One template will not always be enough, and that is fine. The answer is not to start generating, it is to have more than one.

Keep a dictionary of templates, every one of them written and reviewed. Then write a pure function that maps the shape of the data to one identifier. No holdings and no groups gives you the empty template. Groups present gives you the grouped one. Otherwise the flat one. Three things matter about that function. It is deterministic, so the same inputs give the same screen and you can test it. It asserts that the identifier exists, so there is no path where an unexpected shape falls back to something generated. And it logs the identifier alongside the surface, so what a customer saw is a commit hash plus a data model rather than a guess. The agent is choosing between reviewed options. It is never composing one. That distinction is the whole thing your reviewers care about, and it is worth writing down in exactly those words when you take this to them. One more detail worth copying: make that function total. Every shape of data should map to some template, including the shapes you did not expect, because the alternative is an exception path at request time, and exception paths are exactly where unreviewed behaviour creeps in. An explicit fallback template that says we could not render this is still a reviewed screen.

There is one more move that saves you templates, and it is the one teams miss most often.

Suppose two screens differ only in that one shows the amount large and one shows it normal. The instinct is two templates. But variant is a property like any other, so you can bind it to the data model instead of fixing it. The agent sends h2 or body in the data, and the structure is identical. That works for anything the catalog models as an enumerated property: text variants, button variants, row and column alignment, list direction. There is a limit, and it is the one we hit earlier in this series. The value has to be one the catalog already allows, and an unknown value renders an error chip rather than throwing, so you validate against the catalog schema before you send rather than finding out on a customer's screen. Which sharpens the test into three cases rather than two. Varies in how many: a template with a bound list. Varies in degree: a bound enumerated property. Varies in kind: a second reviewed template. Most of what teams call non-deterministic turns out to be the first two.

One more property of this approach is worth having, because it solves a problem that usually gets solved badly.

Because structure and data are separate messages, they do not have to arrive together. This function sends create surface and update components the first time, and after that only the data model. Which means you can put the skeleton on screen before the data exists. If your positions service takes two seconds, send the structure immediately and the data when it lands, and the customer sees a real screen rather than a spinner. And because the data model can be replaced repeatedly, you can stream in stages: the summary as soon as you have it, the holdings when the slower call returns. The client diffs each one. Nothing about the template changes, and you never had to decide in advance what a loading state looks like, because the loading state is just the screen with less data in it. And because the client keeps the structure, a reconnect does not mean re-sending it. You send the data model again and the screen is restored.

Now the honest part, because this pattern is not universal.

First, version zero point nine has no conditional rendering. You cannot say render this card only when the list is empty. You can bind text to an empty string so it takes no space, or bind a list to nothing so its template produces nothing, but a container bound to nothing still draws its own box. That is why the empty state here is a bare text rather than a card: I built it as a card first and it left an empty rectangle on every other screen. Second, variation in kind is still structure. A payment that needs a date picker and one that needs a dropdown are two templates, not one template with clever data. Third, if the set of possible screens is genuinely open ended, no fixed set covers it, and that is the case where the constraint is doing its job by telling you the requirement is wrong. Which gives you a test you can apply in a design review. Ask whether the thing varies in how many, or in what kind. How many is data, and one template covers it. What kind is structure, and it needs another reviewed template, or the variation needs to move into a bound property like a variant. There is a fourth limit worth naming, which is version drift. These enumerations are catalog properties, so they can change between catalog versions independently of the protocol. Pin the catalog identifier you author against, and treat a catalog upgrade as a change that needs the same snapshot tests as a template change.

And if the kind variation keeps multiplying templates, there is one more move, and it is the one your team is already positioned for.

Stop adding templates and add a component. A custom component has a name, a property schema, and a composable content function, and inside that content function you are writing ordinary Compose in your own repository. So an equity renders three lines, an option renders strike, expiry and delta, and a bond renders coupon, maturity and yield, all from one component with one wire name. The agent just sends component position row with a kind property bound to the data. The reason this satisfies the constraint is worth being precise about. That branching ships inside your binary. It goes through code review, your test suite and release sign-off, exactly like any other screen code. It is not generated, it does not cross the wire, and an agent cannot alter it. What an agent can do is say render a position row with this data, which is the same kind of statement as render a text with this string. The cost is real: a custom component is a renderer change on every platform you support, which for you means doing it on Android and on the web and on iOS. So it is worth it when one component collapses five templates, and it is not worth it for a one-off. But since your team is building custom renderers anyway, this is not extra work, it is the thing you were already going to build, used deliberately.

Before the governance piece, here is the test applied to real requirements, because that is where this becomes useful on a Monday.

These are the kinds of lines that end up in a ticket. A positions list of anywhere from zero to four hundred rows: how many, so one template with a bound list. Show unrealised profit and loss in red when negative: that is degree, so bind a property and add no template at all. Retail customers see four summary rows and advisors see nine: still how many, same template, longer list. Options positions needing strike, expiry and delta where equities do not: that is how many detail rows, which is already a template, unless options genuinely need a different component, and then it becomes kind. A wire transfer needing a date picker where an internal transfer does not: that is kind, so a second reviewed template, and that is the right answer rather than a failure. Whichever of forty disclosure blocks apply to this product: that looks like the worst case and it is actually how many, one disclosure template against a bound list of text. And the last one, the screen should adapt to whatever the customer asks for: that is unbounded, it is not a data problem, and the correct response is to push back on the requirement rather than to reach for generation. Seven requirements. Two templates. That ratio is typical once you start classifying properly, and it is the number worth walking into the room with.

Which leaves the question your reviewers will actually ask.

Six practices make this hold up. Keep templates in version control, so a screen change is a pull request rather than a database row. Give each one an identifier and let the agent name only identifiers that exist, rejecting anything unknown at the edge instead of falling back to something generated. Validate the data model against a schema before you send it, because a good template plus bad data renders a wrong screen rather than an error. Snapshot test each template against a fixed dataset, the way the conformance suites in the A2UI repository do. Log the template identifier with every surface, so when someone asks what the customer actually saw, the answer is a commit hash plus a data model and you can replay it exactly. And review the set rather than each screen. That last one is the whole argument: once a template is approved, every dataset it can render is approved with it, which is precisely why this satisfies a constraint that generated UI cannot. And one practical note on the last point: review the template alongside a representative dataset, not on its own. A reviewer looking at a component tree cannot picture forty rows. A reviewer looking at the template plus the empty case, the one case and the many case can.

So, to put it together. Non-deterministic data is not the same problem as non-deterministic structure, and the two get conflated constantly. Cardinality, depth and content are all data, and the template form of children handles all three from a component tree you wrote and reviewed once. Reach for a second template when the kind of thing changes, not when the amount does. Your brokerage payload is already four template bindings deep, so the pattern is proven in your own codebase; what is missing is naming it, writing the test for how many versus what kind, and putting the governance around the template set so your reviewers can approve a catalogue instead of approving screens one at a time. That is a smaller piece of work than building a generation pipeline you would then have to defend. If you want a concrete next step, it is a short one. Take the brokerage payload you already have, and write down which of its four template bindings are how many and which are what kind. Then take the last ten screen requirements that came through, and classify each one the same way. My expectation is that eight of them are cardinality, one is degree, and one genuinely needs a new template. Put that number in front of whoever owns the constraint, because the argument you want to make is not that templates can be made to cope. It is that the variation they are worried about was never structural in the first place.
